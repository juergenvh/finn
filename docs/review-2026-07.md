# finn — Code-Review 2026-07

> Vollständiger Review über vier Spuren: **Server/API-Korrektheit**, **Security**,
> **UI/Frontend** und **Engineering-Hygiene** (Tests/Build/Doku). Jeder Fund wurde
> gegen den tatsächlichen Quelltext verifiziert. Severity-Skala:
> critical / high / medium / low.

## TL;DR

finn ist für sein Stadium **überdurchschnittlich sauber gebaut**: strikte
TypeScript-Konfiguration überall, `npm run check` und `npm test` laufen fehlerfrei
(58/58 Tests), klare Modulgrenzen, disziplinierte ADR-/Docblock-Referenzen, keine
committeten Build-Artefakte, keine ungenutzten Dependencies. Die Front-End-Security
(Markdown → DOMPurify → Mermaid, nonce-basierte CSP, durchgängig parametrisiertes
SQL) ist bemerkenswert sorgfältig.

Die Probleme clustern an drei Stellen:

1. **Netzwerk-/Trust-Grenze** — Server bindet ohne Auth an alle Interfaces; die
   Connector-Subsysteme sind eine SSRF-/Secret-Exfiltrations-Fläche. (Security)
2. **Die Kanten, die der Happy Path nicht berührt** — WebSocket-Boundary ohne
   Input-Validierung und ohne Error-Handler, ausgehende HTTP-Calls ohne Timeout,
   Query-String-Handling ohne die Sorgfalt der Request-Bodies. (Server)
3. **Integrations-Drift nach schnellen UI-Rewrites** — der Carta→MarkdownComposer-
   Umbau (#177) und die Top-Nav-Umstellung (#147) haben kaputte Nähte und ~450
   Zeilen toten Code hinterlassen; Fehlerpfade sind fast durchgehend stille
   `return`s. (UI)
4. **Prozess, nicht Code** — kein CI, kritische Server-Pfade ohne Tests. (Hygiene)

Keiner der Funde erfordert einen Architektur-Umbau — es sind fast alles lokale
Härtungen. Priorität vor jedem Einsatz außerhalb von „ein vertrauenswürdiger Nutzer
auf localhost": die drei Server-High-Findings und die zwei Security-Critical/High-Findings.

## 🔴 Kritisch / Hoch — zuerst angehen

### Security

**S1 (critical) — Keine Authentifizierung auf irgendeinem Endpoint; Server bindet an `0.0.0.0`.**
`server.js:43` (`HOST ?? '0.0.0.0'`), `src/hooks.server.ts` (setzt nur Header, kein
Auth-Guard), `src/lib/server/ws/attach.ts:283-289` (Upgrade-Handler ohne Auth/Origin-Check).
Jede REST-Route und der `/ws`-Socket sind komplett offen. Ohne explizites `HOST`-Override
ist der Dienst im gesamten LAN erreichbar. Wer den Port erreicht, kann alles lesen,
Agenten/Kanäle/Settings ändern und via S2 nach innen pivotieren.
**Fix:** Default `HOST=127.0.0.1`, Auth-Layer in `hooks.server.ts`, WS im Upgrade-Handler
authentifizieren (Shared Secret / Session-Cookie) vor `handleUpgrade`.

**S2 (high) — SSRF + Exfiltration beliebiger Env-Variablen über Connector-`base_url` + `token_env_var`.**
`src/lib/server/db/agent-config.ts:23,27,74,78` (`base_url` nur als URL validiert,
`token_env_var` beliebiger String); `connectors/openclaw.ts:219-243`,
`connectors/openai-compatible.ts:77-113`. Der Server POSTet an die frei wählbare URL
und hängt `process.env[token_env_var]` als Bearer an → (a) SSRF gegen interne Hosts /
Metadata-Endpoints, (b) Leak beliebiger Prozess-Secrets an einen angreiferkontrollierten
Host. In Kombination mit S1 unauthentifiziert remote auslösbar.
**Fix:** `base_url` auf Host/Scheme-Allowlist beschränken (private/link-local/loopback
blocken, `https:` erzwingen), nach DNS-Auflösung erneut prüfen; `token_env_var` auf eine
kleine Allowlist bekannter Key-Namen pinnen (oder Feld streichen und pro Connector
hart verdrahten); `redirect: 'manual'` setzen (siehe S4).

**S3 (high) — Kein Origin-Check beim WebSocket-Upgrade (Cross-Site-WebSocket-Hijacking).**
`src/lib/server/ws/attach.ts:283-289` (Routing nur nach Pfad, `Origin` nie geprüft);
Broadcast an alle Clients bei `:402-408`. Eine beliebige Webseite, die der Operator
im Browser öffnet, kann `ws://localhost:3000/ws` aufmachen, den kompletten
Nachrichten-Stream mitlesen und `user_message`/`approval_decide`/`forward_message`
senden — funktioniert auch im „localhost-only"-Setup.
**Fix:** `req.headers.origin` im Upgrade-Handler gegen Allowlist prüfen, sonst vor
`handleUpgrade` ablehnen. Zusammen mit WS-Auth aus S1.

### Server / Korrektheit

**SV1 (high) — Ausgehende `fetch`-Calls zu LLM-Backends ohne Timeout/AbortController; Stream-Dauer unbegrenzt.**
`connectors/openclaw.ts:242`, `connectors/openai-compatible.ts:109`. Ein Backend, das
die Verbindung annimmt aber nie antwortet (oder mitten im SSE hängt), lässt
`streamOneAgent` (`registry.ts:308-323`) ewig warten → Bubble streamt endlos, Inflight-Row
bleibt `streaming`, und in `handleApprovalDecide` löst `Promise.all` (`handle-approval-decide.ts:114`)
nie auf → `markRouted` (:195) läuft nie → Approval hängt dauerhaft in `approved`. Nur
Prozess-Neustart hilft.
**Fix:** AbortController mit Timeout auf beide Connector-`fetch`; Stream-Gesamtdauer kappen.

**SV2 (high) — `only_rejected`-Filter im Protocol-Viewer filtert *nach* dem SQL-`LIMIT` → Seiten- und Pagination-Bug.**
`src/lib/server/protocol.ts:171-198`. `candidates` wird auf `limit+1` gekappt, *dann* JS-seitig
auf rejected gefiltert, und `overran` auf der gefilterten Menge berechnet. Bei 10.000
Nachrichten mit 500 rejected (keine in den neuesten 201) liefert
`GET /api/protocol?only_rejected=1` **0 Rows mit `next_cursor: null`** — und
`/api/protocol/export` exportiert eine leere/abgeschnittene Audit-Datei. Ältere
rejected-Rows sind unerreichbar.
**Fix:** Rejected-Filter in die SQL-`WHERE` ziehen, dann `LIMIT` anwenden.

**SV3 (high) — Kein `'error'`-Listener auf akzeptierten WebSockets (noch auf dem `WebSocketServer`).**
`src/lib/server/ws/attach.ts:291-366`. Ein unbehandeltes `'error'`-Event wirft (Node-
EventEmitter-Semantik). Ein ECONNRESET oder invalides Frame eines Clients auf wackligem
WLAN → **uncaught exception → gesamter Node-Prozess (inkl. HTTP-Server) crasht**, killt
alle laufenden Agent-Streams.
**Fix:** `'error'`-Handler auf jedem Socket und auf dem `WebSocketServer`.

**SV4 (high) — Eingehende WS-Nachrichten werden nicht validiert (zod ungenutzt auf dieser Fläche), und jedes `decision !== 'approve'` gilt als Reject.**
`handle-approval-decide.ts:50-53`, `ws/attach.ts:294-364`. `decision === 'approve' ? approve : reject`:
ein malformed Frame (`"Approve"`, `undefined`, Tippfehler) **rejected die Approval
terminal** — `rejected` hat kein Undo, der beabsichtigte Agent-Relay ist dauerhaft verloren.
Ebenso fließen `user_message` ohne String-`channel_id`/`body` bzw. `forward_message` mit
Nicht-Array-`target_agent_ids` ungeprüft in die Handler.
**Fix:** zod-Schemas auf der WS-Boundary; unbekanntes `decision` als No-Op/Fehler
behandeln, nicht als Reject.

### UI / Frontend

**U1 (high) — @mention-Popup rendert off-screen: kein positionierter Ancestor.**
`MentionPopup.svelte:74-89` (`position:absolute; bottom:calc(100%+0.25rem)`),
`+page.svelte:1436-1442` (Popup direkt im `<footer>`), `:1861-1868` (Footer ohne `position`).
`bottom: calc(100%…)` löst gegen den Initial Containing Block auf → Unterkante landet
über dem Viewport, `overflow:hidden` verhindert Scrollen. Der Carta-Refactor (#177)
entfernte den `position:relative`-Wrapper; #182 stellte nur die Variablen wieder her,
nicht den Positionierungs-Kontext. Feature wirkt tot, obwohl „restored".
**Fix:** `position: relative` auf `footer` (oder Composer+Popup in positioniertes div wrappen).

**U2 (high) — Enter wird vom MarkdownComposer verschluckt, bevor die Mention-Auswahl greift.**
`MarkdownComposer.svelte:44-48` vs `+page.svelte:958-963`. `handleKeydown` fängt
`Enter && !shift` → `preventDefault(); onsubmit()` *bevor* an den Parent-`onkeydown`
weitergereicht wird. Wer `@dix` tippt und Enter drückt, um den Kandidaten zu übernehmen,
**sendet stattdessen `"…@dix"` in den Kanal**. Nur Tab funktioniert (unsichtbar, s. U1).
**Fix:** `onkeydown?.(e)` zuerst aufrufen, bei `e.defaultPrevented` Submit überspringen.

**U3 (high) — Aus der Zwischenablage eingefügte Bilder können nie rendern — der Sanitizer strippt `data:`-URLs.**
`MarkdownComposer.svelte:97-122` (Paste fügt `![image](data:…base64…)` ein),
`markdown.ts:239-241` (nicht-`https:` → `src` entfernt), `images.ts:95-98`
(src-loses `<img>` → Literal-Fallback). Feature #180 und die https-only-Policy aus
ADR-0023 widersprechen sich im ausgelieferten Code: der Kanal füllt sich mit einer
riesigen Base64-Wand als Monospace-Text, der mehrere MB gehen über WS in die DB.
**Fix:** Bild an einen Server-Endpoint hochladen und https-URL einfügen — *oder*
`data:image/*` im Sanitizer erlauben (mit Größen-Cap). Vorher entscheiden.

**U4 (high) — Kein WebSocket-Reconnect: eine einzige Trennung legt die Session lahm.**
`+page.svelte:613-632` (`onclose` setzt nur `connected=false`),
`settings/+page.svelte:687-721` (gar kein `onclose`/`onerror`). Kein Retry/Backoff,
kein Nachladen verpasster State. Dev-Server-Neustart, Laptop-Sleep oder Netzwerk-Blip →
Composer wird still deaktiviert, streamende Bubbles frieren ein, Approvals aktualisieren
nicht mehr. Einziger Hinweis: ein kleiner hohler Punkt; einzige Rettung: manueller Reload.
**Fix:** Reconnect mit Backoff + sichtbares „reconnecting…"-Banner, `loadChannelData(activeChannelId)`
bei Reconnect erneut ausführen.

**U5 (high) — Scroll-Disziplin in beide Richtungen kaputt: toter ResizeObserver + bedingungsloses Bottom-Yank.**
`+page.svelte:257-292` und `:304-316`. (a) Der ResizeObserver-Effect hängt nur an
`messageScroller`, läuft einmal beim Mount (Liste noch leer) und beobachtet die damaligen
`children` — später gemountete Bubbles nie; scrollHeight-Wachstum feuert ohnehin nicht.
Der in ADR-0016 §8 dokumentierte Mechanismus ist praktisch inert. (b) Der Initial-Scroll-
Effect liest `messagesByChannel[activeChannelId]` (bei jedem Delta neues Array) → läuft
ständig und ruft `snapToBottom` bedingungslos. Wer während eines langen Streams hochscrollt,
wird bei jedem Delta zurückgerissen.
**Fix:** Bubbles beim Mount beobachten (oder einen inneren Wrapper / MutationObserver),
Snap auf `isUserAtBottom` gaten.

## 🟡 Mittel

### Server

- **SV5 (medium) — LIKE-Muster backslash-escaped, aber ohne `ESCAPE '\'`-Klausel.** `messages.ts:253`, `protocol.ts:95`. Suche nach `100%` erzeugt `%100\%%`, matcht nur literalen `100\` → `discount 100% off` wird *nicht* gefunden. Jeder Suchbegriff mit `%`/`_` liefert falsche (meist leere) Ergebnisse in Kanal-Suche und Protocol-Viewer.
- **SV6 (medium) — Unvalidierte numerische Query-Params → NaN mit drei falschen Verhalten.** `channels/[id]/messages/+server.ts:39-51` u.a.: `?limit=abc` → `.limit(NaN)` → **500 statt 400**; `?before=abc` → leeres Resultat (UI meldet fälschlich Ende der History); `?budget=abc` → `budgetBytes=NaN`, Loop bricht nie ab → bis zu **5000 Nachrichten** statt Budget-Cap.

- **SV8 (medium) — `channels/+server.ts:80-88`: Channel- + Member-Insert nicht in Transaktion.** Fehler nach dem `channels`-Insert hinterlässt halb angelegten Kanal; Client bekommt 500 und läuft beim Retry in einen 409-Namenskonflikt. better-sqlite3/drizzle bieten synchrone Transaktionen — keiner der Multi-Statement-Writes nutzt sie.

## Prozess / Engineering-Hygiene

- **P1 (high) — Kein CI.** `.github/` existiert nicht. Nichts läuft bei PRs: kein `svelte-check`, kein vitest, kein Playwright, kein Build-Check. `playwright.config.ts` referenziert `process.env.CI` an drei Stellen, aber es gibt kein CI, das es setzt. `docs/lessons.md` dokumentiert selbst zwei Regressionen (#77, #79), bei denen die lokalen Checks bestanden — die Netze existieren, werden aber nur per Konvention durchgesetzt.
- **P2 (high) — Kritische Pfade ohne Test-Coverage.** Die 6 Unit-Tests decken nur Peripherie ab. Ungetestet: `approvals.ts`, `handle-approval-decide.ts`, `handle-user-message.ts` (Kern-Routing), `handle-forward.ts`, `loop-defence.ts`, `connectors/registry.ts`, `sse-parser.ts`, `ws/attach.ts`, `export-channel.ts`. Der Approval-Flow — die Headline-Invariante des README — hat auf keiner Ebene einen Test. Der eine gut getestete Modul (`inflight-writer.test.ts`, echtes SQLite + Fake-Timer) zeigt, dass das Team es kann; das Muster ist nur nicht auf die wichtigen Teile angewandt.
- **P3 (medium) — Kein Lint/Format-Tooling** (kein eslint/prettier/biome).
- **P4 (medium) — Markdown-Tests prüfen eine gespiegelte Kopie, nicht den Produktions-Hook.** `markdown-links.test.ts:9-19`, `markdown-images.test.ts:18` re-implementieren die DOMPurify-Config statt das echte Modul (jsdom ist bereits devDep) — eine Regression im echten Sanitizer (sicherheitsrelevant) schlägt hier nicht fehl.

## Struktur-Beobachtungen (kein Defekt, aber lohnend)

1. **Dispatch-Logik 3–4× kopiert.** Der Block „Cap-Gate + `Promise.all(streamToAgent)` + Outcome-Persist + Nested-Mention-Rekursion" ist in `dispatchAutoApprove`, `dispatchAutoApproveNested` und inline in `handleApprovalDecide`/`handleForwardMessage` dupliziert. Der Kommentar bei `handle-approval-decide.ts:202` sagt „consolidate only if a third caller appears" — der dritte und vierte existieren. SV21 ist ein direktes Symptom.
2. **Query-Param-Parsing dupliziert** über protocol, protocol/export, messages, search, approvals. Ein gemeinsamer zod-basierter Query-Parser würde SV6 und SV20 an einer Stelle beheben.
3. **zod gut auf REST-Bodies, aber nicht auf der WS-Boundary (SV4) noch auf Query-Strings.**
4. **Live/Dead-Duplikation** (zwei Agent-Editoren, zwei Export/Import-Implementierungen, zwei Validierungspfade) ist die wahrscheinlichste Quelle der nächsten Regression — ein Dead-Code-Sweep als eigener PR lohnt sich.
